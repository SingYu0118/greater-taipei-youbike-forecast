# 簡報內容架構

最終簡報只在取得五日 metrics 與 production URLs 後撰寫。本大綱定義每頁所需故事與證據。

| 頁 | 白話標題 | 證據或視覺 | 講者目標 |
|---|---|---|---|
| 1 | 一小時後，哪裡會有車？ | 產品截圖與一句目標 | 立即建立使用者問題。 |
| 2 | 空站與滿站是時機問題 | 即時風險地圖 | 解釋站點預測的重要性。 |
| 3 | 沒有歷史，所以收集本身就是模型一部分 | 五日收集時間線 | 展現完整資料問題的負責範圍。 |
| 4 | 每個 raw response 都能重播 | Pipeline 架構與失敗邊界 | 展現可靠性與可稽核性。 |
| 5 | 目標很簡單，正確對齊不簡單 | `t` 到 `t+60m` 與容忍時間線 | 不用術語解釋 label construction。 |
| 6 | 我們只使用預測當下已知的資訊 | 特徵可用性時間線 | 讓 leakage prevention 容易理解。 |
| 7 | 過去研究改變了四個設計決策 | 證據到決策矩陣與簡短 citation | 說明採用、延後的內容，以及為何不必推翻架構。 |
| 8 | 多個模型在未來時間窗公平競賽 | Rolling-origin folds 與模型表 | 證明選擇公平。 |
| 9 | 勝出模型擊敗強力的「等於現在」baseline | Final holdout MAE/RMSE | 陳述主要量化結果。 |
| 10 | 表現會依時間、天氣與站點改變 | Subgroup errors | 坦誠呈現營運弱點。 |
| 11 | 近期流動、時間與位置驅動預測 | 白話 SHAP summary | 解釋全域 drivers。 |
| 12 | 如果一小時內開始下雨？ | 控制情境比較 | 展示有用的模型反應實驗。 |
| 13 | App 將模型變成決策工具 | 現場產品流程 | 展示搜尋、地圖、不確定性與解釋。 |
| 14 | 五日能證明管線，不能代表每個季節 | 誠實限制表 | 展現判斷力，避免過度聲稱。 |
| 15 | 多一個月能改善校準與營運 | 優先路線圖 | 以具體下一步與業務價值收尾。 |

## 最終簡報寫作規則

- 每頁只有一個結論。
- 標題陳述結論，不只是主題名稱。
- 技術詞首次出現時以一般英文解釋。
- 每個 metric 都標明時間切分與樣本期間。
- 規劃工作絕不寫成已完成。
- 圖表標明單位、樣本數、baseline 與改善方向。
- 詳細演算法與 schema 放在 appendix 或技術文件。
